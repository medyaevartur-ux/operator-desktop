# Выпуск v8 и откат

## Состояние и границы

Текущий кандидат `8.0.0-beta.3` (Android versionCode 8000003) — редизайн, политика приглашений, диагностика доставки; ниже история beta.1. Кандидат `8.0.0-beta.1`. 14.09.2026 после «я закрыл едже, го» собраны Windows x64 EXE и Android ARM64 APK. Они находятся в `releases/8.0.0-beta.1/`; подписи и hashes проверены, см. artifact-manifest.json. На устройства не устанавливались, production и канал автообновлений не переключались. Команда prepare-release по-прежнему готовит отдельный комплект сервера/web/виджета без установщиков.

Сайт: `https://zhivaya-skazka.ru`; сервер: `5.129.241.152`; сервис: `alphabet-chat-api`; прежний каталог: `/opt/alphabet-chat-api`; порт: 3010. БД общая с Alphabet. Изменять только перечисленные таблицы чата. Маршруты магазина, включая `/api/upload` на порт 3000, сохранять.

Новый сервер требует JWT оператора и подписанную идентичность посетителя. Клиент 7.1 и старый виджет с ним несовместимы. Сначала готовятся клиенты и обновление загрузчика сайта, затем согласованное переключение. Нельзя возвращать небезопасную авторизацию по одному visitor/session ID ради совместимости. Старая история остаётся операторам; анонимному посетителю без секрета нельзя автоматически отдать прежнюю переписку.

## Комплект без установщиков

```powershell
powershell -NoProfile -File scripts/prepare-release.ps1
```

Команда запускает клиентские регрессии, сборку интерфейса/виджета, TypeScript API и серверные policy-тесты. Каталог записан в `prepared-v8/LATEST.txt`:

- `chat-api.tgz`: исходники/скомпилированный API, SQL-миграции, lockfile, скрипты, манифест файлов;
- `operator-web.tgz`: собранный интерфейс/PWA;
- `widget.js` и `widget.min.js`;
- `widget-release.tgz`: исходник виджета, неизменяемые `widget.v8-<sha16>.min.js` и `loader.v8-<sha16>.js`, `widget-release.json` с SHA256. Загрузчик собирает сам упаковщик (`scripts/package-prepared-release.mjs`), руками его больше не готовят; нажатие кнопки сайта «Открыть чат» до загрузки виджета он запоминает и выполняет;
- `release_chat.py`, `rollback_chat.py`, `prepare_chat_env.py`;
- `release-manifest.json`: SHA256 и размер каждого артефакта.

Ключи, `.env`, данные клиентов, uploads, node_modules, EXE/APK/AAB в этот комплект не входят. Исходники Windows/Android остаются в `src-tauri/`.

## Серверные проверки до выпуска

Разрешённый тестовый каталог: `/opt/alphabet-chat-api/.codex-v8-work`. Единственная разрешённая на этом сервере тестовая БД: `codex_chat_v8_test_20260914`; метка `chat_v8_test_marker=synthetic-only`. `.env.test` хранится только на сервере с правами 0600. Тесты сами отказываются от другой БД/хоста; FCM/WebPush отключены через `PUSH_DRY_RUN=true`.

```sh
cd /opt/alphabet-chat-api/.codex-v8-work
npm ci
npm run build
npm test
```

Перед передачей кандидата исключить секреты и сравнить SHA256 архива на обеих сторонах. Применённые SQL `001`–`004` не редактировать: runner проверяет checksum и блокировку. Новые изменения схемы оформлять следующей миграцией. CI поднимает собственный PostgreSQL 16 с синтетическими данными; CI не деплоит и не строит установщики.

## Закрытая конфигурация

`ops/prepare_chat_env.py` без флагов показывает только готовность. `--apply` создаёт `/opt/alphabet-chat-api/.env.chat-v8` с правами 0600 без рестарта и миграций. Сохраняются существующие JWT и Firebase `zhivaya-skazka-operator`; отдельные VAPID-ключи остаются на этом сервере. Никаких секретных значений в логах/архивах.

Внешние push содержат только идентификаторы и фиксированное общее уведомление. Текст для локального отображения загружается с собственного API после проверки сеанса/устройства и настроек предпросмотра.

Web/PWA (iPhone, браузер) живёт на отдельном origin `https://operator.zhivaya-skazka.ru` (DNS A → 5.129.241.152 с 01.10): только статический `operator-web.tgz`, API остаётся на `https://zhivaya-skazka.ru`. Нельзя раздавать панель вместо магазина на `/`.

- `scripts/deploy-operator-web.ps1` без ключей — план (только чтение): DNS, сайт nginx, сертификат, релизы, свободное место и правки nginx, которые ещё не применены (наша перезагрузка применила бы и их, поэтому выкладка при таких правках отказывается).
- `-Apply -Archive prepared-v8/<релиз>/operator-web.tgz` — релиз в `/var/www/operator/releases/<время>`, атомарная ссылка `current`, хранятся 5 последних. Первый запуск получает сертификат Let's Encrypt (webroot `/var/www/operator/acme`, при продлении nginx перезагружается сам) и пишет сайт `/etc/nginx/sites-available/operator.zhivaya-skazka.ru`; nginx перезагружается только если сайт изменился и `nginx -t` прошёл.
- `-Rollback` — вернуть предыдущий релиз (nginx не трогается).
- Кэш: всё перепроверяется (`no-cache`, ответ 304), `/assets/` — год и immutable. Маршрутов в адресе у приложения нет, поэтому неизвестный путь — 404, а не оболочка. Открытое приложение после выкладки само перезагружается, если не нашло файл старого экрана.
- iPhone: уведомления работают только в приложении с экрана «Домой» (Safari → «Поделиться» → «На экран „Домой“»), разрешение — по кнопке «Включить» в полосе сверху. Каждый push заканчивается уведомлением не позже чем через 5 с, иначе Safari отзывает подписку.

## Переключение production после готовности клиентов

1. Проверить текущий Git diff, версии, подписи клиентов, manifest/SHA, 25 серверных интеграций и актуальные локальные проверки. Не выкладывать стабильный автоапдейт без проверки на устройствах.
2. Подготовить обновление загрузчика виджета с версией в URL, например `/widget/widget.min.js?v=8.0.0-beta.1`. Изменение HTML/компонента магазина выполняется только в рамках согласованного переключения; закрыть/перезагрузить старые вкладки. Старые закешированные клиенты нельзя заставить поддерживать новый протокол одним рестартом API.
3. Получить свежий read-only план:

   ```powershell
   powershell -NoProfile -File scripts/deploy-server-v8.ps1
   ```

4. После готовности клиентов вызвать тот же скрипт с `-Apply -ClientsReady -Archive <путь-внутри-проекта> -ExpectedLiveSha <свежий-digest> -ExpectedNginxSha <свежий-digest>`. Эти флаги не являются заменой решения о выпуске. Скрипт сверяет digest повторно под блокировкой.
5. Выпуск создаёт неизменяемый `/opt/alphabet-chat-api/releases/v8-<UTC>`, устанавливает lockfile-зависимости, сохраняет chat-only dump на том же сервере и прежние конфиги. Затем применяет additive-миграции, меняет только свой systemd drop-in и добавляет `/api/chat-v8/`, `/api/invitations` → 3010. Перезапускается только `alphabet-chat-api`.
6. Проверяются `/health`, неавторизованный `/api/chat-v8/devices` → 401 и главная магазина → 200. При сбое конфигурация/сервис откатываются автоматически. БД назад не восстанавливается: новые сообщения нельзя потерять.
7. Выложить совместимый виджет через `scripts/deploy-widget.ps1 -ExpectedRemoteSha <свежий-SHA>`. Для v8-исходника скрипт сначала требует живой `/api/chat-v8/meta`; со старым API откажется до загрузки файлов. Убедиться, что SHA исходника и min-файла соответствует комплекту. Для точечного legacy hotfix можно передать отдельные `-SourcePath`/`-BundlePath`.
8. Проверить авторизованный диалог на явно тестовом посетителе, перезагрузку страницы, потерю сети, дубликаты, вложения, передачу и доставку уведомления. Не писать настоящим клиентам для проверки.

## Повторный выпуск и выпуск только виджета

Боевой nginx уже содержит блок `# Codex v8 widget loader`. Повторный выпуск его не удаляет и не дописывает второй: `install_routes` проверяет, что блок совпадает с установленным байт в байт, и меняет в нём только имя `loader.v8-<sha16>.js`. Если блок правили руками, выпуск останавливается и просит сверить nginx вручную.

```powershell
# Только чтение: печатает состояние и diff nginx для загрузчика из архива (архив не загружается)
powershell -NoProfile -File scripts/deploy-server-v8.ps1 -WidgetArchive prepared-v8/<каталог>/widget-release.tgz
# Только виджет поверх живой v8, без рестарта сервиса и без миграций
powershell -NoProfile -File scripts/deploy-server-v8.ps1 -Apply -WidgetOnly -WidgetArchive prepared-v8/<каталог>/widget-release.tgz -ExpectedWidgetSha <widget_sha256 из плана> -ExpectedNginxSha <nginx_sha256 из плана>
```

Выпуск виджета проверяет живой `/api/chat-v8/meta`, кладёт хешированные файлы рядом со старыми (старые остаются для закешированных страниц), атомарно меняет `widget.js`/`widget.min.js`, делает `nginx -t` и reload, затем проверяет, что главная магазина отдаёт новый загрузчик, а сам загрузчик и бандл отвечают 200. При любом сбое возвращает nginx и файлы виджета. Резервная копия — `/var/backups/zhivaya-chat-codex/<UTC>-widget`.

Локальные проверки инструмента выпуска: `python -m unittest ops/test_release_chat.py`.

## Откат

Каждый выпуск сохраняет `/var/backups/zhivaya-chat-codex/<UTC>-v8/manifest.json`, прежний nginx, drop-in, исходники и chat-only dump. Каталог/дамп приватные. Успешный выпуск записывает digest конфигов для последующего сравнения.

```sh
python3 rollback_chat.py --backup /var/backups/zhivaya-chat-codex/<UTC>-v8
# После проверки плана:
python3 rollback_chat.py --backup /var/backups/zhivaya-chat-codex/<UTC>-v8 --apply
```

Ручной откат откажется, если текущий release, nginx или его drop-in изменились. Он возвращает прежний каталог сервиса и маршруты, **не выполняет down/reset/restore БД**. Выпуск только виджета откатывается тем же `rollback_chat.py --backup .../<UTC>-widget` (возвращает nginx и два файла виджета). Откатывать по порядку, начиная с самого нового выпуска: после выпуска виджета откат полного выпуска откажется, пока не откачен виджет. Резервные копии старого `deploy-widget.ps1` (без nginx) восстанавливаются только вручную. Автоматический и ручной production-откат подготовлены, но намеренно не запускались на живой v8, поскольку она ещё не активирована.

## Windows и Samsung S22 Ultra — нативные пакеты и пересборка

До сборки: Node 22, Rust 1.94, Visual Studio C++/Windows SDK; для Android JDK 17, SDK 36/NDK 30. Проверить свободную память; один worker. Не менять pagefile и не завершать чужие процессы.

Версии в package/lock, server package/lock, Cargo/lock и tauri.conf согласованы. Android `bundle.android.versionCode=8000001` для beta.1; каждый следующий опубликованный APK, включая stable, должен иметь больший code. Ключ подписи сохранять для совместимости. Исторический `release.keystore` уже находится в Git: не включать его в новые публичные/передаваемые архивы и не менять без отдельного решения. Пароли находятся в игнорируемом `keystore.properties` или переменных среды.

Проверки исходников без установщиков:

```powershell
$env:CARGO_BUILD_JOBS='1'
cargo check --manifest-path src-tauri/Cargo.toml --lib -j1
cargo test --manifest-path src-tauri/Cargo.toml --lib -j1
& ./src-tauri/gen/android/gradlew.bat -p src-tauri/gen/android :app:compileArmDebugKotlin --no-daemon --max-workers=1 '-Dorg.gradle.jvmargs=-Xmx1536m -Dfile.encoding=UTF-8' '-Pkotlin.compiler.execution.strategy=in-process'
```

Для разрешённой пересборки Windows: `scripts/release.ps1 -Version 8.0.0-beta.3 -Notes <текст> -BuildInstallers`. Подпись обновления ждёт ввода пароля ключа (28.09 фоновая сборка без терминала остановилась именно на этом шаге), поэтому запускать в своём терминале и вводить пароль самому. Без ключа в окружении сборка всё равно создаёт установщик и завершается ошибкой только на подписи обновления. Скрипт требует существующий ключ updater, проверяет версии и готовит JSON через сериализацию. Сам ничего не публикует.

Android ARM64: `npm run tauri -- android build --apk --target aarch64 --ci`. Затем `scripts/prepare-android-update.ps1` получает APK и заранее проверенный SHA256 прежнего сертификата, проверяет подпись/package/version/code, готовит `android-latest.json`; ничего не устанавливает и не публикует. Встроенное обновление также проверяет HTTPS, размер, SHA256, package ID, сертификат и versionCode перед системным установщиком.

Приёмка на устройствах: вход/выход и смена аккаунта, foreground/background, сон и перезагрузка S22, offline→online, уведомление без текста в push-транспорте, открыть нужный чат, прочитать/ответить из уведомления, повторы, DND, восстановление неотправленного ответа, Windows трей/автозапуск и обновление поверх прежней подписи. Без этих проверок статус остаётся beta.
